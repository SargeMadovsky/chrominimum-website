A minimal shell for the modern web.

Chromium Embedded Framework handles pages, JavaScript, and PDFs. The Rust shell keeps the essential navigation controls. The aim is to reduce interface overhead while retaining security protections.

Chromium remains a substantial browser engine. Lower memory use and faster browsing on real websites have not yet been demonstrated.

Local measurements · October 24, 2026

Lower idle memory. Faster startup.

We compared ChroMinimum, ungoogled-chromium, and Google Chrome on one PC: local page startup, idle, video playback, and a three.js game. All 75 runs passed the measurement checks.

312 msDirect test-core startup to HTML readiness. UC: 380 ms; Chrome: 703 ms. Medians of 10 runs with a warm OS cache.
201 MiBIdle private bytes. UC: 260 MiB; Chrome: 332 MiB. Medians of 5 runs.
Smooth playback and renderingNo reported dropped video frames. Game p99 render-loop interval was about 6.2 ms in all three browsers.

There are trade-offs. During video playback, CM used 7–9% more private bytes. Game CPU was about 12% higher than UC and nearly equal to Chrome. The CM–UC difference was about 0.16 percentage points of whole-machine CPU on this PC.

Method and limitations

Test PC: Windows 10, Ryzen 7 3700X, 32 GiB RAM, Radeon RX580, 165 Hz display. Tests ran in a separate Windows account with disposable clones of prepared synthetic browser profiles. The measured viewport was 1000×600 at DPR/scale=1. Browser order rotated between rounds.

Versions: CM — Chromium 154.0.8037.98; ungoogled-chromium — 155.0.8059.79; Google Chrome — 155.0.8059.85. The products are compared as a whole; shell and engine-version effects were not isolated. Chrome was extracted from its official installer rather than installed system-wide.

ChroMinimum started directly through the test core bootstrap, bypassing the installed launcher/updater. The 312 ms figure does not measure the full installed-browser startup path. Startup runs from process creation to receipt of a local HTML page's HTTP signal after two requestAnimationFrame callbacks. The OS cache was warm; this is neither cold startup nor an external measurement of pixels appearing on screen.

Idle: 5 seconds to settle, then 30 seconds of observation. Video: 10 media seconds of warmup, then 60 seconds. Game: 10 seconds after scene readiness, then 60 seconds. Video used a local synthetic file; the game used a pinned three.js scene with the same camera motion. Real Internet sites were not part of this series.

Memory and CPU were sampled once per second for current-session processes with executables inside the test browser's directory. Final CPU counters were retained for discovered processes after exit. Processes outside that directory or entirely between samples were not counted. The first and last 1.5 seconds of resource windows were excluded.

Chart CPU values are normalised to one logical core: 100% means one fully occupied core. Divide by 16 for whole-machine percentages on this 16-thread PC. GPU load, VRAM, and energy consumption were not measured.

The separate observer used a median of about 1.31% of one core and about 73 MiB of private bytes. These costs are not included in browser metrics; observer-induced effects were not measured separately. OS background services remained active, so background load was not fully isolated.

All 75 runs were accepted and the browsers exited normally. Summaries were recomputed from raw samples without discrepancies. Render-loop intervals and browser drop counters do not replace external measurement of physical frame presentation.

Current implementation

Working today. Still an early experiment.

Available features are listed separately from architectural plans. Alpha builds are for experimentation, not for replacing your main browser.

In the published Windows build

  • Websites and PDFs through Chromium Embedded Framework.
  • Address bar, back / forward, reload / stop.
  • Menu, About window, saved window size, and basic keyboard shortcuts.
  • Windows: per-user installation, EN/RU selection, and opening local HTML/HTM/PDF files.
  • A minimal shell without tabs or user extensions.

Plans and limitations

  • A fully modular feature system and compatible extensions.
  • WebExtensions without artificial restrictions on network filtering.
  • A finished download manager and permissions system are not available yet.
  • No independent security audit or demonstrated speed advantage on real websites yet.

Windows has an updater that verifies core-package signatures; the installer itself is not Authenticode-signed. Linux/macOS builds are experimental and have no updater; macOS builds are not notarised.
